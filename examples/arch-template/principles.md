# 通用代码与架构原则

这些要求适用于各前端、后端场景。具体层次、目录和工具由场景说明决定，不要求不同语言和工作负载使用同一套物理结构。

## 职责与可理解性

- 使用明确的业务名称，同一概念保持同一术语。代码名称表达对象和动作；注释解释业务原因、并发约束和技术取舍。
- 模块承担内聚职责，通过小而明确的接口供调用方使用。规则、状态和验证尽量集中在负责的模块，减少修改一个功能时触及无关业务。
- 遵循单一职责、依赖倒置和组合优先；新增层、接口或共享模块必须承担当前存在的责任。没有对应职责就不建立空层。
- 模块之间的依赖应明确且可检查。文件划分不形成编译器约束，需要严格隔离时使用包或模块边界。

## 按场景选择内部结构

| 主要复杂度 | 推荐组织方式 |
| --- | --- |
| 业务对象、规则和状态转换 | 应用用例、业务模型和外部实现分工，按需要采用 COLA 的职责划分 |
| 请求、任务或资源的执行顺序 | 明确操作流程、状态、取消、超时和恢复，不额外建立通用流程引擎 |
| 选择、评分和调度 | 策略算法与自有运行状态，独立验证输入、时间和并发行为 |
| 配置、查询及报表 | 保持清晰用例和存储查询，规则增长后再补相应模型 |
| 页面、交互与异步数据 | 业务功能、组件、交互状态和接口访问分工，不复制后端四层 |

职责分层和业务模块是两个维度。场景模板确定目录和依赖之后，采用项目必须按该契约扩展，不由执行者临时更换架构。Go SaaS 模板固定为业务模块内 application/domain 两个独立包、HTTP 与技术实现外置；网关和前端分别遵循其场景契约。架构调整必须先更新规范、样板和检查，再通过明确版本应用。

## 数据与依赖

- 业务规则与数据库、界面、网络细节分离。模块定义自己需要的接口，具体实现依赖该接口所在模块，入口负责组装。
- 模块不得绕过接口直接访问其他模块的内部实现或表。事务、并发和副作用必须保持业务操作所需的一致性，拆模块不能拆坏原子性。
- 前后端以 API 契约连接，明确输入、输出、权限、版本、可空值、金额、错误和取消语义。客户端类型与校验不替代服务端规则。
- 共享部分只承担确实通用的责任；技术栈、场景或项目特有逻辑保留在对应位置。

## 规范归档与验证

目标仓库应有明确位置存放业务知识、技术与架构约定、编码和测试规范；根 AGENTS.md 明确引用。人类与 Agent 使用同一份规范。

确定的格式、依赖、类型和构建要求由规则及工程工具执行；架构职责、业务逻辑归属和不必要的复杂度由模型结合业务与代码评审，重要发现附证据复核，再进入项目审查。行为、事务和并发由适当测试验证。不能因依赖图无违规就认定划分合理，也不能因模型给出意见就认定存在缺陷。

模板、规则校验、模型评审和目标项目验收分别记录，不用目录、测试数量或架构总分代替交付效果。

参考思想见 [COLA](https://github.com/alibaba/COLA)；具体 Go 和 Vue 的采用范围见各场景说明。
