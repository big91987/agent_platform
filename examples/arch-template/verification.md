# 工程校验与验收

本页将规范对应到工具、测试和评审，供各场景组合使用。目标是提供可扩展到多种语言的架构校验与评审能力：以 ArchUnit 式规则检查确定的约束，以模型评估代码职责、模块划分和架构风格是否合理。当前 0.2 实现了 Go 与 TypeScript/Vue 的统一依赖规则、完整评审材料、命令/模型 HTTP 接入及引用核验，配套独立模板与本地回归。实际命令和限制以 [工具说明](tool/README.md) 为准。模型架构质量、外部 CI 和目标产品验收不因这些实现而视为完成，验证证据见 [validation.md](validation.md)。

## 跨语言架构校验

项目选择场景模板后，明确采用的架构原则、业务职责、接口和允许的依赖；可机械执行的部分写成配置。工具从实际代码获取结构、依赖、关键实现及位置，分别执行规则校验和模型评审，输出有来源的发现，接入本地检查及项目既有审查／返工流程。

| 能力 | 应承担的责任 |
| --- | --- |
| 项目架构声明 | 表达哪些代码属于哪个模块、允许哪些依赖及公开入口；不强迫所有场景采用四层 |
| 语言分析 | 解析所支持语言的包、模块、导入等事实及源码位置；明确解析、路径解析和动态行为的限制 |
| 统一规则判定 | 校验依赖方向、模块边界、公开接口访问及循环等规则；不按语言分别维护含义冲突的规则体系 |
| 模型架构评审 | 结合业务用例、架构原则及相关代码，判断职责、内聚、耦合、逻辑归属、架构适配及不必要的抽象 |
| 诊断与门禁 | 区分规则违规、经证据复核的架构发现及待确认事项，输出位置、依据和影响，供人类、Agent 和 CI 使用 |

首版先验证 Go 与 TypeScript／Vue，再按语言接入能力扩展。面向多语言的设计不等于已经支持所有语言；不支持、未解析或缺少必要事实时必须报告检查不完整，不能算通过。跨语言的 HTTP／RPC 调用关系需要接口契约或其他可靠证据，不能从目录或名称推断。

自然语言说明表达原则、职责和设计原因，可执行配置承担确定的架构约束；两者需要一致。规则变更进入评审，不能为了让一次代码改动通过而静默放宽要求。架构合理性纳入模型评审范围，业务正确性、事务和并发仍需适当的测试验证。

## 模型怎样评估架构合理性

模型需要读取实际代码及其业务背景，不能仅凭目录名、文件长度或一张依赖图判断架构质量。首次分析从项目结构和主要用例形成可核对的实际架构视图；有已确认基线后，后续评审可集中于改动及受影响模块。没有架构规范时，可以探索候选结构并指出假设，不能把推测当作项目已经接受的设计。

| 评审对象 | 需要回答的问题 | 应寻找的证据 |
| --- | --- | --- |
| 业务模块划分 | 不相关职责是否集中，同一业务规则是否散落，修改是否牵连无关模块 | 具体用例、调用方、状态归属、重复规则及实际修改记录 |
| 分层是否发挥作用 | 四层是否只有目录，业务规则是否混进接口或持久化，用例层是否承担全部业务 | 关键方法、决策位置、事务边界及调用关系；简单 CRUD 不强行要求富领域模型 |
| 模块内聚与接口 | 调用方是否必须了解大量内部细节，是否绕过模块自身约束 | 导出操作、参数、内部字段访问及多个调用方的用法 |
| 请求与状态管理 | 网络流程、状态和副作用是否可追踪，配置／权限／观测是否混用 | 请求生命周期、状态更新、取消与失败路径；不能以静态审查代替真实并发测试 |
| 前端职责 | 页面、交互、接口和共享状态是否混杂，状态所有权和作用域是否清楚 | Vue 组件、composable、store、watcher 和请求回写路径 |
| 抽象是否必要 | 新层、接口和共享部分是否只转发，是否增加了理解和修改成本 | 独立规则、状态、生命周期、当前变化需求及调用方收益 |

例如，规则可以发现领域代码直接依赖数据库；模型进一步判断业务判断是否仍堆在应用层。模型也应识别为了形式分层造成的大量空转发。文件大、类多或依赖多只是调查线索，不能直接判为设计缺陷。

建议的最小执行方式是：

1. 固定本次源码和规范版本，收集结构摘要、业务说明和相关实现。模型能按问题继续查调用方、状态和测试，不只接收一段截断代码。
2. 规则执行确定校验；模型提出候选架构问题，说明依据及可能反例。两类检查可以独立发现问题，不能只对规则已经报错的文件运行模型。
3. 核对引用文件、位置和依赖是否真实存在，再对重要候选补读相关实现、测试及约束，过滤误报。只有证据不足时才追加评审，不默认每个问题运行多轮多 Agent。
4. 统一交付：问题是什么、发生在哪里、违反哪项原则或职责、具体影响是什么、最小调整建议及需要怎样验证。事实、推断和待确认项分别表述，不输出没有依据的架构总分。

模型评审不是确定性判定器。规则违规可以直接阻断；模型发现进入项目既有审查及返工门槛，重要发现经复核后可以要求处理，不能把模型自报的置信分当作客观依据。业务背景不足、未读关键实现和模型运行失败都明确列出，不冒称架构已全面通过。

## 模型评审的验证与使用成本

先用少量人工已确认的正反例验证：符合分层但职责堆积、简单合理的 CRUD、必要的运行状态模块、过度抽象、前端状态混杂。观察有效发现、误报、遗漏及建议是否引入无效复杂度，不能只用发现数量评价能力。

保留源码、规范、模型及评审配置版本，实际分析范围、发现、证据复核结果、耗时和可得用量。完整基线与增量评审分别记录，避免每次改动都重复分析全仓。跨语言覆盖按实际样例验证，不能因模型能够阅读某语言就宣称具备相同精度。

模型接入复用已有受支持执行能力；启用外部模型时明确凭据引用和代码发送范围，不默认发送整个仓库，不复用旧任务凭据。本轮不复用旧任务凭据，外部模型服务需由采用项目显式配置；受控传输测试与真实模型样例分别记录。

## 现有能力与复用评估

这一能力是独立工具工程，不能用几个语言检查命令的串联或一段泛泛评审提示词代替。现成项目先评估复用：

- [archfit](https://github.com/alexei-led/archfit)：公开说明包含多语言结构分析、预期架构配置、模块及依赖规则、CI 结果；尚未在本仓验证语言覆盖、误报和缺失事实处理。
- [ArchGuard](https://github.com/archguard/archguard)：提供多语言分析与架构治理，但其公开矩阵中的语法、调用、包及真实项目验证覆盖不同；不能把语法可解析等同于所有架构规则均受支持。
- Arch-Go、go-arch-lint 和前端依赖分析器可作为分析实现或对照工具候选，不预设其输出已经满足统一事实与规则模型。
- [ArchGuard Co-mate](https://github.com/unit-mesh/co-mate)：公开提供 AI 架构辅助与治理方向，但具体能力、语言精度和可运行性尚未验证，不能按项目简介视为已可采用。
- [Anthropic Code Review 说明](https://support.claude.com/en/articles/14233555-set-up-code-review-for-claude-code)：公开流程包含基于代码上下文的模型审查和发现复核。这里借鉴候选发现后的证据验证方式，不据此声称其已经覆盖本工具的架构评估要求。

统一事实与规则、语言接入、模型探索及复核、结果与门禁集成需分别评估工作量。此前模板与迁移估算不代表从零建设通用多语言架构校验与评审工具的成本。

## 通用要求与场景检查

| 范围 | 要检查的内容 | 执行方式 |
| --- | --- | --- |
| 架构依赖 | 模块及职责的允许依赖、公开接口与内部实现 | 语言分析提供事实，由统一架构规则判定 |
| 架构合理性 | 模块内聚、职责归属、架构适配及过度抽象 | 模型结合用例与代码探索，重要发现补充证据复核 |
| 基础质量 | 格式、类型、静态错误、依赖完整性和构建 | 项目固定工具和版本，任一步失败传播非零退出 |
| 规则与交互 | 业务规则、状态、错误、并发、取消和恢复 | 独立规则测试、组件测试及必要集成测试 |
| 接口契约 | 请求、响应、权限、版本、金额和未知值语义 | 消费端契约及真实服务集成测试 |
| 完整用户旅程 | 页面操作、真实 API、副作用、失败恢复及结果 | 组合项目的端到端测试和独立 QA |

场景约束放在 [Go SaaS](backend/go/saas/README.md)、[Go 模型网关](backend/go/model-gateway/README.md)及 [Vue 管理控制台](frontend/vue/admin-console/README.md)中；项目组合后形成适用的架构声明。格式、类型、构建和行为工具继续各司其职。前后端检查可独立运行；联合验收使用组合项目选定的实际后端和生产前端产物，不固定为某一种技术组合。

## 校验工具自身的验收

1. 固定工具版本，使用独立小型样本验证当前语言、语法、模块和路径配置；同一规则类型分别验证 Go 与 TypeScript／Vue，证明共用判定含义。
2. 每条自动规则有合规和违规样本，确认退出码、问题定位及覆盖范围。这属于工具回归，不是产品缺陷或产品验收。
3. 缺工具、缺配置、解析失败和未覆盖文件明确报错或报告限制，不能默认为通过。
4. 保存被检版本、工具版本、范围、诊断和退出码。优先采用工具原有 JSON 输出，按项目产物策略留存。
5. 新初始化目录、目标仓库及实际 CI 分别复验，不依赖维护者预装的未记录工具。

## 项目入口与交付

目标仓库保留一个完整验证入口，组合所选前端和后端的检查。可提供模块级快速反馈，但不能以局部结果代替完整门禁。

改变技术实现时，原测试按业务行为映射到新测试，明确替代关系和需要真实执行的部分。不能静默删除严格负例，也不要求新实现保留旧内部函数或文件名。

工具中的模型评审辅助判断模块划分、规则完整性及无效复杂度，结果进入项目既有设计与代码审查；完整测试和独立 QA 评价实际行为。规则结果、模型发现、完整门禁、PR、合并和部署分别报告。

记录实际修改范围、有效发现、构建测试耗时、恢复与人工介入。未迁移模块明确保留待办，不能通过全局忽略规则把全仓标为合规；不以规则数或代码量直接推断提效。
