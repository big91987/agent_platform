# 模型网关参考

## 分工

本例展示完整单次派发和流式取消，不实现完整 MaaS 产品。请求流程和路由状态分别拥有明确职责，不复制业务后台四层。

- httpapi：模型请求协议校验、HTTP 状态和 SSE flush。
- gateway：选择目标、打开上游、提交输出、复制流、关闭资源；不自动重试或跟随 3xx 跳转。
- routing：按已知响应头延迟选择；维护互斥保护的状态和配置版本。锁只覆盖本地计算，不跨网络。
- infrastructure/upstream：真实 HTTP 请求及响应资源，复用客户端连接；错误返回流程层。
- cmd/gateway：组装、监听地址及超时。

## 约束及扩展位置

客户端取消必须传到上游，首帧不得等完整输出才出现。提交输出以后错误不能改写状态或重放请求；调用方需要依据日志/实际结束判断截断。配置变更清除旧观测；旧版本结果不参与新选择。

参考策略只比较已知响应头延迟，无探索、健康冷却、迟到样本排序、SLO 或公平性保证。模型供应商协议、鉴权、原子准入及结算由目标项目接入明确接口；不要因为目录齐全就声称生产能力齐全。固定服务使用唯一 target ID 和递增配置版本。

新增重试时需要明确尝试与请求、提交点和幂等约束；新增计费时由业务用例保持准入/预留与完成/结算的原子性，不能把事务搬进 routing。

## 运行与验证

```sh
go test -race ./...
go vet ./...
go build ./...
UPSTREAM_URL=http://127.0.0.1:9000/v1/chat/completions go run ./cmd/gateway
```

监听 127.0.0.1:8081，接受 model=chat。UPSTREAM_URL 指向完整请求地址；本例未配置供应商凭据，不自动使用任何本机密钥。测试用真实本地 HTTP/SSE 服务验证首帧、取消与错误路径，这不是供应商兼容性或产品 QA 结论。
