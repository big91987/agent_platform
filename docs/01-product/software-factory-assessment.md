### 目标和已经确定的边界

我们建设的是**受控研发流程与软件工厂的工具链**。让研发、测试团队能够用明确的角色、工程步骤和人工检查，搭建并持续使用自己的 Harness；用真实项目证明可靠性和收益。当前不以成熟通用低代码平台、全套组织治理或多云资源平台为目标。

- 环境方案优先采用 **OpenSandbox**，平台管理任务执行环境的申请、关联和释放。此为选型方向，不代表 SDK、原生执行器、恢复和文件访问已经完成集成或实测。
- **Example 是复制进项目并按项目调整的示例。** 项目的 Workflow YAML、准备脚本、测试入口和交付配置应在项目仓库中维护。Runner 不应通过平台安装目录去执行 Example；也不要求每接一个仓库都在平台维护专属脚本。
- 通用平台代码、通用工程工具仍有明确维护源和版本。项目定制是合法工作，升级应提供可审阅差异；不能用“唯一来源”否定项目自己的 Harness，也不能把复制的通用缺陷补丁当标准交付。
- 研发、独立产品测试和部署保持独立流程；测试组可以配置不同深度的测试。测试发现问题后，由人或受委托协调者带报告创建修复任务，当前不新增自动跨流程调度。
- 保留角色独立会话、交接记录和必要人工检查。同一 Run 共用工作区，不等于所有角色合成一个 Agent，也不等于所有流程共用一个环境。
- 新方案在独立分支/worktree、平台端口与数据目录、独立验证 Pipeline 中实施验证；不直接切换既有运行环境。

### 最小职责划分

| 谁负责 | 本期做什么 | 不应承担什么 |
|---|---|---|
| 项目仓库与 GitHub Workflow | 保存项目 Harness；核验事件来源，提交任务、仓库和版本；按项目规则执行 CI/CD | 依赖平台源码路径，或要求临时 Runner 目录一直存活供异步 Run 使用 |
| Agent Platform | 保存任务与角色输入，执行流程/Gate/权限，关联执行环境，呈现日志、材料及恢复入口 | 判断具体产品的测试覆盖是否专业，内置某产品的 RPM/TPM 规则 |
| OpenSandbox | 按所选部署方式提供隔离执行环境及操作接口；具体生命周期行为需集成验证 | 自动理解 SOP、决定产品通过、代替长期预发环境的发布流程 |
| 项目初始化及工程步骤 | 在任务环境内检出指定版本、安装依赖、就绪检查、固定测试与发布 | 把各仓库差异变成平台的一组固定业务节点 |
| Agent 与 Skills | 承担需求、设计、实现、测试规划/评审/执行及报告等专业职责 | 自行授予权限、伪造工程回执或决定资源管理权限 |

推荐主路径：`Issue → 仓库内入站 Workflow → 平台受理并去重 → 分配执行环境 → 可见的项目准备步骤 → 各角色/Gate/工程步骤 → 结果回 GitHub`。部署继续走独立发布流程；测试环境可以访问另一套已部署系统。

环境分配是执行前提；项目准备是流程中可见、可配置的工程步骤。后者复用命令执行能力，不为“clone、npm ci、启动服务”分别新增节点类型。初始检出与仓库脚本有先后依赖：须先取得受信指定版本，才能执行其中的准备脚本；不能把“已有本机工作区”继续作为新环境入口的隐含条件。具体配置形式在执行位置确认后设计。

### 下一个先确定：Agent 在哪里运行

**建议：Agent 原生执行器与该任务的工程命令、浏览器在同一执行环境中运行；平台服务留在环境外管理流程。** 这样 Agent 编辑的文件、固定测试读取的文件和浏览器访问的任务服务可以保持一致。角色原生会话仍各自独立。

另一种方式是 Agent 留在平台宿主、通过远程工具操作环境。它可以保留部分现有执行链，但需要约束 Agent 的本机工具、处理两侧文件与服务访问差异；对当前以原生 Coding Agent 为主的路径，预计增加衔接复杂度。因此不作为首选，但此判断需要小范围技术验证，不是已完成选型证明。

这项待用户讨论确认后，做有界技术验证：原生启动与双向消息、工具调用/审批、停止与异常退出、平台重启后同会话接续、文件读取和浏览器访问。验证应使用受支持接口，不能以一次 shell 成功冒充完整原生执行链可用。若协议或会话状态不能可靠保留，先明确限制，再决定是否值得增加适配。

### 环境保留：先覆盖实际人工检查

以下是建议，不是已确认保留期限：执行和短期人审期间保留环境；任务结束后按策略停止计算并保存所需工作文件、原生会话状态和正式产物，之后显式或到期清理。文件保留、进程存活、内存快照是不同承诺，首期不承诺内存级恢复。环境丢失或已释放时，不得悄悄新建环境并冒充原会话接续。

平台用已有 Run ID 关联 OpenSandbox 返回的环境标识，不再引入同义任务 ID。GitHub 重复投递、创建结果未知、平台重启时先核对已有动作；不能重放未知副作用。管理凭据留在受信平台侧，Issue 参数不能自行指定任意宿主挂载、放宽执行权限。正式报告及需供人审的材料应在环境释放前归档到既有持久位置，不能让报告链接依赖容器一直存活。

### 收成三批工作，而非一次重做平台

| 顺序 | 平台/工程工具 | Example 与测试仓 Harness | 能说明完成的结果 |
|---|---|---|---|
| 1. 环境与接入闭合 | 验证原生执行链；接入一种 OpenSandbox 部署方式，贯通申请、执行、文件、停止与恢复 | 示例复制入仓；项目准备/校验在任务环境中执行；入口提交任务及指定版本 | 第二仓无需平台源码目录即可启动；同 Run 文件一致；重复入站不重复环境；准备失败不进入研发；停止/重启不丢身份或重放不明动作 |
| 2. 流程配置做减法 | 梳理 Agent、人工 Gate、命令/外部动作、结束节点的配置；区分外部连接配置与执行动作 | 显式人审点、少量受信任务参数、工程步骤的输入输出约定；专业测试计划及独立评审 Skills | 配置者能指出在哪里准备、谁检查、如何退回、产物在哪；保存重载后实际执行一致；可跳过人审不能跳过固定测试或权限审核 |
| 3. 独立流程与交付验证 | 复用现有日志、关联和结果展示；只补真实缺口 | 独立研发与测试流程，GitHub 可查看报告；部署独立选择环境；人带报告发修复任务 | 正常、返工、人工等待、外部失败及恢复均有真实证据；区分产品结果与 Harness 可靠性，并记录人工救援成本 |

命令节点负责运行代码/脚本，GitHub 等连接配置负责凭据和访问；不再用一个模糊的 Connector 名称解释这两类事情。是否调整底层类型另行评估，不为术语改名立即拆出多层对象。报告内容由 Agent/Skill 生成；要求可靠发布时，优先复用已有固定发布节点及远端回执，而不是重造报告中心。此为建议，具体发布方式仍待确认。

首期不做多供应商环境插件市场、弹性集群、内存快照、完整环境控制台、通用变量编程语言和自动跨 Pipeline 派单。旧本机入口和在途 Run 按原定义保留；新保证通过明确版本和标准升级获得。

对收益的验证沿用第 7 节的对照思路，但先衡量最直接的三项：首次/第二仓接入的人力、正常任务中的非预期人工救援、实际验收与遗留缺陷。角色分工和必要人工检查是业务约束，不能通过删除这些环节制造“提效”。

用户后续确认：面向服务器部署与团队使用，任务执行环境由平台管理更合理；近期先采用平台分配目录、初始化命令节点执行项目准备脚本的简单方案。GitHub 提交任务和仓库/版本等参数，平台接收任务后准备工作区。下文“GitHub 先准备目录再调用平台”的表格、主路径及 P1/P3 对应措辞保留为此前讨论记录，已被本段方向替代；具体 API、配置和保留策略尚未定案，未实施代码改造。

本次评估范围：现有同机执行方式下，以 Run ID 关联平台分配的目录，复用命令节点执行 checkout、项目初始化和就绪检查。指定版本在首次准备时解析并记录，恢复不能再次跟随移动分支取到另一版；缺材料或准备失败不进入业务节点。原有显式 workspace_path 入口和在途 Run 继续兼容。工作目录管理不等于容器/虚拟机安全隔离，也不承诺从干净操作系统重建。长期预览/预发环境继续由独立部署流程管理。

| 报告生成与发布 | Agent/Skill 生成报告、Dashboard 和证据；发布到 GitHub 应评估工程化节点与模型自主调用的取舍，尚未由用户确定方案。已有固定发布器是评估起点 |
| 测试与研发 | 保持两个独立 Pipeline。测试发现问题后由用户或受委托协调者创建修复 Issue，带同版报告，触发研发；当前不自动创建修复任务或跨 Pipeline 调度 |

建议的近期主路径是：`Issue → GitHub 环境准备与初检 → 带任务参数和环境引用调用平台 → 角色执行/显式 Gate/交接 → 结果与报告回 GitHub`。研发后部署另走现有项目部署流水线；测试后是否起修复任务由人决定。

仍需设计的接口问题：GitHub 的一次 job 结束后，平台异步 Run 仍可能运行，不能假设 Runner 临时目录/临时服务自然持续可用。应明确环境所在宿主与平台执行器的可达关系、准备回执、复用/占用和清理责任；当前同机可先用持久任务目录及受控隔离实例，不据此引入远程 Worker。准备完成与平台持续执行是两个不同生命周期。

### 实际使用中的责任组、测试层级与环境（用户补充确认）

- 研发 Pipeline 自带实现阶段的测试与质量检查；专用产品测试 Pipeline 承担更独立、更端到端的质量验证，不能用前者通过代替后者通过。
- 正常生产使用中，研发与测试责任组各自构建、维护针对本项目的流程。测试组可以配置多种深度的 Pipeline，例如较轻的检查与更完整的端到端验证；这些是可配置的流程组合，不要求平台写死固定测试等级。
- 当前由协调者构建这两类流程，是用户委托其验证平台和 Harness 能力的实验分工，不能据此推导生产使用中所有流程都由 Builder 设计或裁决产品质量。
- 研发流程、不同测试流程所需的依赖、数据、工具与服务环境可以不同；环境准备仍由项目在 GitHub 工程链中定义，平台接收正确环境引用。一个 Run 共用工作区，不意味着所有 Pipeline 必须共用同一个环境。
- 部署可选若干指定环境，供体验、不同组的专项目标及测试组人工验证。自动化测试报告不替代人工实际检查。具体环境名称、数量、隔离和部署选择后续设计，不先落实为固定生产/预发层级。
- 明确区分执行 Agent 的工作区/工具环境与被测试的已部署系统。测试 Pipeline 可在自己的工作区编写/运行测试，访问另一指定部署环境；不必把产品源码复制进每个测试阶段。

对平台的近期要求是：让各组能复用组件和专业 Skill 配置各自流程，显式指定 Gate、合法任务参数与环境引用，并查看各自的报告和人工意见。是否需要额外的组权限、环境占用管理或统一质量看板，要根据实际使用问题再评估，不能仅因存在多个责任组就引入组织治理系统。

## 1. 判断与评估边界

**当前已经具备有价值的编排执行底座，但距离“可复用的受控研发流程与软件工厂”还有明显的产品化距离。主要问题是控制规则、工程准备和交付关系分散在平台、模板、脚本、提示词以及协调者操作中，用户要自行把这些拼成完整流程。**

这不等于底层都应重写，也不等于所有 Python 脚本都是临时补丁。现有安装清单、来源校验、GitHub 入站去重、固定命令回执、私有报告发布已经是可复用实现。真正没有收口的是：哪些保证由谁承担、怎样配置、怎样看结果、换项目和升级后是否仍成立。

用户已确认的定位和约束：

- 服务于受控研发流程与软件工厂；角色分工、SOP、阶段交付及必要人工检查是产品价值的一部分。
- 平台测试中，Builder 建设与验证 Harness，产品 Pipeline 承担产品实现和验收；不能靠 Builder 代做来掩盖缺口。
- 做减法，先分析现有问题，再讨论抽象。不能把每次特殊情形都变成一个新对象、新节点或开关。
- 当前是可信同机、自托管、低并发实践。组织治理、远程 Worker、分布式调度、通用低代码语言不是本次默认目标。

本报告使用三类证据：**实查**指本次页面/源码直接观察；**历史**指已有验证记录描述的事件，未在本次重新执行；**建议**指尚待评审与验证的改进。没有对平台总可靠性、跨仓复用率或工程提效给出虚假的百分比。

## 2. 先按用户工作看问题

| 用户/责任方 | 要完成的工作 | 当前主要障碍 | 平台应提供的最小承诺 |
|---|---|---|---|
| 项目接入者 | 把现有仓库接入一条可用流程 | 安装器、外部 Skills、Runner、独立 checkout、浏览器、GitHub、部署分别准备 | 一次检查清楚依赖、缺项、维护来源和可用范围；同配置能重复安装 |
| 流程配置者 | 表达角色、顺序、交付、人工检查及例外 | 画板只显式表达部分执行关系，其余散落在长指令/脚本 | 看得懂阶段职责、输入输出、决定者、检查条件及失败去向 |
| 任务发起者 | 带材料发起需求、修复或测试 | 网页要求本机路径；Issue 材料有专门协议；权限选择不贯通 | 不需要理解安装内部结构即可提交，输入不能自行扩大权限 |
| 阶段执行 Agent | 完成本职工作并可靠交接 | 需要自行恢复文件、理解多层规则及环境限制 | 能拿到正确版本的必要材料、角色能力及明确交接对象 |
| 人工检查者 | 审阅产物、批准或退回 | 有审批节点，但缺少紧凑、同版的审阅包和持续有效的批准依据 | 看到当时那份产物，知道批准什么，改动后原结论不被误用 |
| 维护者 | 定位阻塞、修复并接续 | 日志完整，但信息跨页面，恢复决策仍重度依赖专家 | 状态、影响、证据及合法下一步集中可见，未知副作用不重放 |
| 结果使用者 | 看报告、PR、部署和遗留问题 | Run 完成与产品完成容易混读，本地路径和下载附件不直观 | 一眼分清执行结束、验收结论、发布状态和实际访问入口 |

当前可承诺“持久执行和受控转移”；尚不能直接承诺“任意仓库开箱即用”“每个交接都被同版审核”“无需专家即可恢复”或“明显提高研发效率”。

## 3. 已有能力应保留，不能误诊成全部缺失

1. **执行事实有基础。** Run 保存流程及 Connector 配置；节点作用域完成工具、合法边、过期提交和待处理输入校验均在服务端。自然语言说完成不会直接推进。
2. **恢复并非随意重跑。** 工作区独占、停止/回退、持久消息、固定命令日志、通知独立重试及不确定结果核对已经存在。应优化使用方式，而不是另造一套恢复引擎。
3. **人工检查是已有原语。** `approval` 节点和 `qa-rework` 示例存在。问题是标准研发模板没有把人工审阅策略和产物版本组成易用能力，不是内核完全没有人工环节。
4. **配置已有复用。** 独立 Agent 与节点共享执行配置表单；权限、模型、Skills、工具并非全部藏在后台。任务级入口、已保存模板、新任务和在途会话的关系仍需收口。
5. **脚本已有工程纪律。** 安装器通过正式 API，清单校验漂移，仓库入口核验来源与事件身份。维护源 Python/JSON/YAML 中对 `model-relay`、5545、8793 的定向检索未见硬编码命中；这只支持“没有这些特定字面值”，不证明所有环境依赖已解除。
6. **报告自动发布已经进入当前模板。** `product-e2e` 有固定 `report_publish`、`report_notify`；发布器有私有快照、摘要及远端回执核验。历史人工上传缺口不能继续当作当前完全未实现；当前能力仍限定私有 GitHub Release 下载附件，不是在线 Dashboard 托管服务。

## 4. 关键诊断：先讲问题，再决定抽象

### F1｜接入流程仍依赖懂内部实现的人，网页与 GitHub 入口的准备责任不一致

**实查：** 网页启动只有任务、工作区绝对路径等字段；提示用户自备独立目录。安装手册要求独立干净 checkout，GitHub 入站另有准备逻辑及私有配置。历史 Run `29ef…` 页面记录：第一次 prepare 因空目录向上发现平台仓库而拒绝，协调者补好独立 checkout 后才正式接续。来源保护正确；不自然的是“准备独立测试工作区”节点实际上仍有调用者必须先完成的工作。

**影响：** 一个新用户看到“准备工作区”会合理期待它完成准备；一个正确保护机制因此表现成难懂的失败。接第二个项目仍要懂宿主目录、Runner 和脚本约定。

**修订方向：** 先把 GitHub Issue 主入口的项目配置、环境准备和初检做完整，复用已有 clone/来源/独占校验。GitHub 准备好可持续使用的任务工作区和环境后，再调用平台；平台验证引用和访问条件。网页自助选择仓库/置备环境暂不列近期目标，不另建 Project 或环境管理服务。

**完成证据：** 两个不同仓库均能由新接入者按文档启动；空目录、脏目录、错误 origin、工作区占用得到可操作诊断，不能靠 Builder 手工补克隆才通过。

### F2｜画板表达执行线路，尚不足以表达受控阶段

**实查：** 当前研发图 12 个节点、21 条边。1280×720 下首屏只看到前部阶段和交叉回路线，后续阶段需滚动；选择节点后会聚焦相邻边，这个已有能力应保留。节点配置是模型、长角色指令、权限/工具和继续次数；交接页主要表达“去哪儿”。没有在阶段主视图直接展示：依据哪些输入、交哪些材料、谁判断合格、是否要人审。

**实查：** “固定规则流转”实际对应 Agent 固定完成、命令成功/失败或人工选择，不是通用条件表达式引擎。`handoff` / `complete_node`、节点 ID、路由标识露在常用配置里。角色内容可以配置，输入/交付约定主要靠 prose。

**影响：** 用户会把线当成完整 SOP，而真正的门槛藏在别处；要调整业务流程，往往必须同时改图、提示词和发布脚本。

**最小方向：** 保留四种底层节点，不先加“PM、QA、环境、制品、策略”等十几种组件。先提供阶段列表/主路径视图，与高级画板共用同一份定义；阶段面板回答“做什么、依据什么、交什么、怎么检查、下一步”。把模型/执行权限放明确的执行配置，协议名和内部 ID 放高级信息。主流程与返工路径分开展示，但不隐藏真实例外。

**验证方式：** 用需求→人审→开发→测试→QA→交付和明确 Bug 直接研发两条实际流程做任务演练；用户应无需读代码就能指出人审点、交付项及失败去向。不能只用换颜色、自动布局来声称问题已解决。

**审阅后优先项：** 先设计显式 Gate 及受信任务参数的关系。流程定义决定哪些人审 Gate 可按授权选择跳过；任务的自主推荐选项决定本次取值；平台记录真实人工决定或跳过原因，不能把跳过显示成人工批准。无需为了这个用例先增加通用表达式语言。质量条件和执行权限审批与阶段人审分开。

### F3｜交接记录持久，交接内容不等于不可变；人审还缺同版依据

**实查：** `NodeResult` 保存 summary/inputs/artifacts，handoff 验证当前节点与合法路由；没有在该路径统一对文件读取、摘要及快照。文件浏览读的是工作区当前文件。固定完成 JSON Schema 能校验结构，但不能自动证明文档内容、文件存在或版本一致。

**澄清：** 当前同一 Run 的节点共用一份工作区，`workflow_engine.go` 将 `r.WorkspacePath` 传给节点执行；此处讨论的是同一目录内文件随时间变化，不是节点之间有多份源码。路径变量只能指向位置，不能固定当时字节。是否需要额外快照取决于具体人审/审计场景；先用项目 Git 版本和既有归档满足，不把全阶段快照列为已确认平台需求。

**影响：** 人工看到“交接过这个路径”，无法单靠平台保证后来打开还是当时那份。旧评审结论可能指向已变文件。这是用户关心的稳定交接问题，而不是仅增加一段“请保留历史”的指令。

**最小方向：** 在确需验收的阶段支持可选、明确的交付约定；以现有 Run/执行序号/相对路径与内容摘要识别，不先造全局 Artifact ID 和制品中心。保存被接受的交接版本；人工批准绑定该份审阅内容。工作草稿可以继续修改，新的交付不能冒用旧批准。敏感材料、体积、保留周期和访问权限必须沿现有边界处理。

**边界：** 文件快照证明“看的是哪份”，不证明内容专业或真实；内容仍由角色/独立评审/人工判定。原始 Agent 文本保持原样。

### F4｜“测试通过→QA→发布同一候选”仍缺少标准的可信闭合

**实查：** `repository.py::delivery_artifacts` 要求最近 `qa` 完成并走 next，产物在本 Run 文档目录且非空；`publish` 检查分支、冲突和发布文件后 add/commit/push。这里没有统一将 tests/QA 与最终源码树指纹绑定。历史验证多次由维护者逐文件重算 Git 对象/指纹来补这一关系。

**审阅后归类：** 这是工程交付一致性的待评估风险，不是“平台使用了多份工作区”的缺陷，也不先做独立版本治理能力。优先通过项目 CI、Git 版本和发布工具约定验证，必要时再补最小绑定；不排在环境衔接与显式 Gate 之前。

**影响：** 即使每一份结果都真实，也仍可能不是同一候选。人肉逐文件核对属于持续交付成本，不能无限留在协调者职责里。

**最小方向：** 固定测试入口记录受测范围与指纹，QA 明确引用该次测试，发布器检查当前候选是否仍匹配。源代码/测试/构建配置与允许追加的报告要有明确规则，不能简单把测试后新增报告也当成全量失效，更不能通过随意排除目录漏掉产品变化。

**归属：** 通用平台保存不可篡改的执行引用；Git 源树和发布检查由可复用研发工具承担。产品通过条件留给模板和项目。不要在通用内核硬编码 `qa`、`development` 等业务节点名。

**验收：** 测试后改代码、QA 后换候选、仅追加报告、返工后重验四条路径给出正确结果；未知/缺失版本证据阻止发布而不自动重试求绿。

### F5｜图可以自由修改，但模板工具对节点名、角色及目录有隐藏耦合

**实查：** 发布器找固定 `qa`，候选接续找 `publish`，报告发布器找 `prepare`。这些是受信模板内部约定，不等于错误；但在可视化重组、拆分 QA 或替换准备节点时，用户不容易知道依赖。安装器还绑定 Trellis 0.6.15 和面向平台产品/架构的 Skills。

**影响：** “通用组件”表面上能连线，真正支持的变体却取决于代码约定；小型普通应用仍可能继承过重的文档方法和准备步骤。

**最小方向：** 先列明并检查模板的真实契约。工具已有独立责任时，显式声明它消费哪个既有节点结果；先只支持已证明需要的替换/拆分，不建表达式语言或任意 JSON 数据流引擎。Trellis、项目方法 Skill 应是可选择的模板配置及受测组合，不能为了“通用”直接删掉原工程门禁。

### F6｜安装器和页面是两条配置路径，修改与升级责任没有形成自然闭环

**实查：** manifest 漂移保护拒绝覆盖页面修改，是正确防丢失机制。但用户在平台改完后，标准升级需自己比较、合并、决定维护方式。当前 Run 冻结 DB 图和配置，脚本/Skill 磁盘内容不在冻结范围；README 要求使用不可变版本目录，但操作仍由安装者完成。

**影响：** “可以在画板上配”和“可以标准升级”之间有摩擦。Run 显示冻结版本也不能单独证明用到的脚本/Skill 没变。

**最小方向：** 先明确每个配置的维护方和版本。模板默认与本地修改提供可审阅差异，升级不能静默覆盖，也不应要求用户凭记忆合并；不要立即引入复杂多层继承。把不可变脚本/Skill 版本目录与来源摘要纳入现有安装/升级交付，旧任务引用旧文件，新任务用新版本。

**验收：** 全新安装、无变化重入、页面改模型后升级、模板职责变更、半途安装失败、旧 Run 接续都能解释且无丢配置。首期可以保留 CLI，但不能只给本机操作经验。

### F7｜权限已有开关，执行能力却还没有成为任务开始前可验证的条件

**实查：** 网络、提权申请、原生审批方式可配，`auto_review` 不是无条件接受。通用浏览器工具限定 `app` / 静态原型；动态产品测试可额外挂原生浏览器 Skill 和授权，但“挂载了”不证明监听、浏览器、依赖和供应商入口真能用。安装器给各角色 workspace-write；QA 不改产品主要仍靠职责指令。

**影响：** 角色独立会话不等于文件写入隔离；计划评审通过后才发现环境不支持，便形成回退和频繁审批。没有证据说明所有此类申请都不合理，不能把关闭审批作为统一解决办法。

**修订方向：** 项目通过 GitHub Workflow 完成环境初始准备与检查，平台接收环境引用并核验原生执行器实际可用性；依赖装在 Runner 上不等于平台 Agent 可用。复用现有执行配置，权限仍由受信平台和原生审核器决定。QA 生成测试资产和不修改产品的专业纪律由 Skill 明确；环境隔离依项目策略，不能用摘要检查冒充写权限隔离。

**任务参数：** 当前启动 API 有有限 `map[string]string`，Issue 入口主要解析 Issue 号和材料，网页没有相同参数表单。先从材料、受测版本和已授权执行选项这几个真实用例定义输入类型、默认值、敏感性和受信校验；不要先造可变共享全局变量总线，也不能让 Issue 正文自授提权。

### F8｜角色有分工，但职责/评审门槛仍可能诱发无效接力

**历史：** Issue37 曾多次计划→评审→返工；记录明确指出 READY 语义让规划承担完整脚本实现，后来维护源纠正为“计划可交执行准备”。当前模板已修正，不能继续报成尚未修的同一个 bug。

**更广的风险：** 通用规划/QA 指令、角色 Skills、任务正文共同约束，容易产生重叠乃至冲突。当前通用产品测试评审提示词直接列出 RPM、TPM 等模型中转领域项；这个检查对本项目必要，但不能靠给通用提示词不断叠加测试仓特例来获得覆盖。

**修订方向：** 作为独立的 Skill 改进工作，明确“规划、计划评审、测试执行、结果复核、报告”职责和产物；计划评审使用独立 Skill 与节点。具体限额矩阵留在项目依据中，验证 RPM/TPM 不因整理而丢覆盖。平台支持这些角色和交接，不判断测试计划是否专业；先不用新增平台组件解决内容质量问题。

**价值判断：** 独立评审发现规则缺漏是有价值返工；因职责误解、同一材料重复抄写或环境反复失败是流程成本。必须分开统计，不能把全部回退视为坏事，也不能把回退越多当质量越高。

### F9｜运行页以历史和原始输入为中心，任务结果与处理入口不够突出

**实查：** 历史产品测试 Run 顶部是绿色“已完成”及“第33次节点执行”，首屏被原始任务正文占据。下方逐步展开历史、长路径与摘要。节点详情中的本地 artifacts 只是路径文本；HTTPS 引用可点击。实际输入、原生会话、命令日志、报告和 GitHub 结果分在多个入口。

**影响：** 用户问“测得怎样”“卡在哪”“报告在哪”时，需要人工翻译页面。执行生命周期完成是事实，但不是产品验收通过；不能只加免责声明让用户自行辨别。

**最小方向：** 首屏展示本次目标、当前阶段/阻塞、用户待办、已提交的原文结论入口和交付物；原始输入与完整历史折叠可读。优先“查看报告/审阅交付/处理审批/核对外部结果”等对应当下状态的动作。系统只投影受信状态和原始结构化结果，不从 Agent prose 猜测 Go 或自动总结业务。

**报告展示：** 复用已有正式发布回执给出标题、版本、结论来源、下载/在线属性与证据链接。是否托管 HTML 另行决策，不能直接将任意 Agent HTML 与平台同源执行。

### F10｜研发、部署、测试和修复任务的独立关系需要讲清，不能把人工选择一概当平台缺口

**实查：** 研发模板结束于“交付完成·待人工合并”，Run 页面已有 GitHub 交付查询，并非完全没有部署展示。产品测试报告发布也已有正式节点。但产品缺陷→修复任务、同版复测、精确合并→授权部署的完整闭合仍由现有授权和协调者多次核对组织。

**修订方向：** 保持研发与部署、产品测试与缺陷修复各自独立。部署触发和环境选择由项目 GitHub CI/CD 管理；测试完成后由用户/受委托协调者带报告创建修复 Issue。平台准确展示各自结果和关联链接即可，当前不自动串联两个 Run、不自动创建修复任务，也不以有人参与决定下一任务为救援失败。多部署环境另行规划。

## 5. 哪些是胶水，哪些该留在标准工具链

| 当前连接方式 | 判断 | 合理处理 |
|---|---|---|
| Builder 补 checkout、手算候选指纹、手工整理发布链接 | 分别属于接入准备、工程校验、交付呈现，不能都归平台内核 | 项目 GitHub 准备流程和工程工具优先承接，平台只补确证缺失的接口与呈现 |
| 用户/协调者根据测试报告创建修复 Issue | 当前确认的正常使用流程，不是自动化缺陷 | 保留人工判断与两个独立 Pipeline，携带报告及版本引用 |
| `install.py`、`install_github_entry.py` 的来源和漂移校验 | 已有可复用工具，不是一次性补丁 | 保留实现，收口版本、配置所有权、检查和使用入口 |
| `github_entry.py` 的身份、事件键和接单关联 | 合理的渠道适配 | 保留 GitHub 特性在适配器；不由 Agent 读正文决定信任 |
| 固定验证、Git 发布、本机部署工具 | 适合工程工具链，未必适合通用平台内核 | 统一输入输出、证据和恢复契约，不复制成每仓补丁 |
| 产品测试用例、业务断言和供应商预算 | 产品特定责任，不该全部平台化 | Pipeline 按项目文档实现；平台提供执行/权限/证据/预算约束的可靠入口 |
| 手写受信事件和失败恢复状态 | 平台已有生命周期应承担 | 复用持久 Hook、回执、消息、去重，不能再造脚本侧调度状态机 |
| 长提示词重复目录、发布规范和运行限制 | 部分是必要协作约定，部分在替代本应明确的配置/校验 | 对能机器验证的事实做正式校验；判断性职责继续由 Agent 承担 |
| 某份模板绑定平台产品方法、Trellis、宿主标签 | 可用的特定发行组合，通用性有限 | 命名并声明支持范围；通过第二仓证明哪些真正需要可选，非泛化到一切 |

归属原则：平台负责跨场景的授权、输入持久化、执行、交接事实及呈现；模板表达研发/测试 SOP 与角色门槛；工程工具负责仓库/测试/发布的确定性动作；产品仓负责业务实现、断言和项目规则。这是已有责任的划分，**不是建议增加四个服务或四套状态机**。

## 6. 画板改进需要先验证的信息设计

建议先用只读原型讨论以下任务布局，再实施界面，避免先重画一套节点皮肤：

| 操作 | 用户首先应看到 | 高级信息/约束 |
|---|---|---|
| 配置整条流程 | 阶段主路径、必经人工检查、明确起点与结束结果 | 图、全部返工边、内部路由、执行上限 |
| 配置一个阶段 | 职责、输入依据、交付内容、判断方式、失败去向 | 模型/Skill/工具/沙箱及原生参数；共用现有 Agent 表单 |
| 配置外部动作 | 动作及目的、消费哪个结果、可能副作用、失败如何处理 | argv、环境引用、仓库凭据等管理员配置 |
| 发起任务 | 近期以 Issue 模板提交目标、材料、合法选项，GitHub 准备环境 | 网页/其他渠道启动后置，未来复用准备流程 |
| 人工检查 | 待审版本、产物预览、检查意见、通过/退回及后果 | 路由码和原始回执按需查看 |
| 看运行 | 当前进展、阻塞、待办、结论与可访问产物 | 原始任务、逐次节点历史、原生会话和日志 |
| 升级流程 | 新旧差异、本地修改、受影响的新/旧任务 | 安装来源、manifest、不可变依赖版本 |

保留输入预览、原始回执、会话和完整日志；“简洁”不等于删除可追溯性。也不增加单独 Session Prompt 或第二份节点任务说明：职责在角色配置，具体工作在 User Input 和交接。

### 6.1 非 Agent 节点和配置复核（2026-10-11，待讨论）

本节按维护源 `65b4d3e` 的表单、校验和 Example 工具复核，不代表重新验证运行中的全部功能。初步判断：节点种类只有 Agent、人工确认、Connector、结束，数量并不过多；复杂度主要来自职责混合、底层配置外露、输入来源隐含和模板对图的隐藏依赖。下面是改进候选，不是已批准的新产品契约。

判断标准：节点负责一件流程中必须发生的事；连线表达下一步；任务输入表达本次选择；平台负责执行事实、权限和恢复；专业业务判断留在 Agent/Skill。相同需求优先改善现有能力，不默认增加节点、资源对象或表达式语言。

| 对象 | 当前事实或问题 | 最小改进方向 |
|---|---|---|
| Connector | 同一个概念包含本机命令、Issue 关联/创建、评论和 PR 创建；维护配置含可执行路径、固定参数、凭据引用、工作区范围、超时与授权，节点再填写部分业务输入 | 保留已注册、受控操作的能力。画布按“执行检查、发布报告、创建 PR”等动作选择；维护者配置底层实现，编排者配置本次输入和结果去向。不把每个动作新增为引擎节点类型 |
| Connector 输入/输出 | 本机命令读取任务和 previous_results，节点表单没有通用的显式输入映射；repository.py 按 qa/publish ID 查结果，report_publication.py 按 prepare ID 查结果 | 从发布操作开始，声明少量必需输入、输出及来源，用表单选择已声明的结果。缺输入在运行前提示；改节点显示名不影响绑定，删除或替换来源能被检测。暂不建设任意表达式、全局可变变量或通用数据流引擎 |
| 人工确认 / Gate | 已有 approval 节点、确认内容和出站决定；业务人审与原生执行权限审批是两种不同控制 | 复用 approval 表达人审对象、可访问材料、通过/退回与意见；按已确认方向讨论允许跳过的 Gate 和受信任务参数。保持必要质量检查及权限审批各自语义，不为每种业务评审造一个节点 |
| 连线 | 同一编辑器呈现 route、mode、description；Agent 自主交接、固定完成、Connector next/failed、人工选择的含义不同 | 按来源节点呈现：操作为成功/失败，人审为通过/退回；内部路由默认生成并保留稳定引用。避免让用户配置对该节点无意义的模式；不先增加通用条件/循环节点 |
| 结束 | 结束节点停止编排；Run completed 不能说明产品验收通过 | 保留简单结束语义，运行页区分流程结束与报告结论，提供已有产物入口。不让平台从模型文字猜 Go/No-Go，不新增“验收通过”引擎状态冒充专业判断 |
| Hook 通知 | 当前配置事件、节点过滤、评论 Connector、Issue 来源和正文模板，且已有独立回执和去重 | 常用配置收为“向关联 Issue 同步进展/待处理事项/结束通知”，精细事件和模板按需展开。状态通知保持不阻塞；如果发布报告是交付条件，就用显式操作节点并核对回执，不能混用通知成功和交付成功 |
| 任务参数 / 流程设置 | 当前有工作区、入口、授权、节点执行上限等；网页启动没有完整任务参数表单。任意直接入口可能绕过前置材料准备 | 仅声明真实需要的任务选项，统一 Issue/API 的类型、默认值和校验；参数不能自行授予权限。同 Run 工作区沿用已有字段。直接入口只开放准备条件清楚的路径，限制与诊断放高级配置 |
| 保存与布局 | 表单有应用设置，流程有保存，同时部分字段会同步到草稿；节点配置和运行历史暴露许多内部信息 | 明确一套草稿/保存语义；主画布先看主路径、Gate 和异常去向，详细返工线按需展开。ID、坐标和协议内容不占普通操作主视图，完整诊断仍可查 |

Connector 的改进不能停在改名和折叠字段：至少拿现有“发布报告”和“发布代码/创建 PR”两类真实操作证明小接口能隐藏准备、校验、执行和回执处理，且错误输入不会产生外部副作用。工具实现仍由唯一工程维护源安装升级，不在每个测试仓留下新脚本补丁。是否进一步拆出连接凭据资源，应以重复配置和独立生命周期的实际需要判断，不先造 Connection/Action/Binding 多层对象。

对于 Example，先移除发布工具读取特定节点 ID 的隐含约定，改为声明必要来源并在安装、编辑、运行入口校验；不是把项目测试断言或质量评判搬进平台。保留角色和 Skill 的专业分工。研发自测、独立测试、部署仍为各自流程，环境按前述 GitHub 准备约定交接。

优先级建议：将 **Connector 输入输出与模板隐藏耦合复核** 同 Gate/受信参数设计一起纳入 P1；接着在 P3 简化连线、通知和保存配置。用第二个团队改变测试层级、替换报告节点的实际过程验证是否还必须修改脚本。暂不新增并行汇聚、嵌套子流程、任意脚本表达式、平台环境管理器或自动跨 Pipeline 修复链。

## 7. 修订后的提升计划：先接入与 Gate，再分别改进 Skill 和工程交付

以下是顺序建议，非已批准排期。每项用验收证据结束，不用“多了一个页面/节点”结束。依赖不满足不往后堆新框架。

### P0：厘清承诺和责任，冻结最小改进范围

产出：按第0节已确认边界，选择两条独立旅程：Issue 发起研发并可配置人审 Gate；Issue 发起产品测试并交付报告。缺陷修复由用户/受委托协调者另起 Issue；明确修复可按现有入口直接交研发。列明 GitHub、平台、项目与 Skill 的责任。

退出条件：每段准备、交接、检查、发布、恢复有明确责任方；能指出哪些当前仍需协调者。确认人工检查点是流程配置，不是提示词随缘询问；不默认每一阶段加审批。方案冲突先记录，不以先写代码强行定案。

### P1：设计 GitHub 环境交接与显式 Gate（F1、F2、F7）

先明确项目 GitHub Workflow 如何准备研发/测试环境，再给平台传工作区及必要环境引用、准备结果和受信任务参数。定义 Gate 的默认人审、允许跳过的范围、自主推荐参数及运行记录，复用现有人工确认能力。参数名/格式、持久环境占用与清理方案仍需评审，当前不直接实现。

退出条件：Issue 经 GitHub 准备后唯一启动 Run，各节点共用正确工作区；准备失败不误启动、重复事件不重复置备、GitHub job 结束不破坏在途环境。人工 Gate 正常暂停，授权自主模式按定义跳过且如实记录；不可跳过的检查仍生效，参数不能自行扩大权限。停止/恢复和环境清理职责明确。

### P2：分别完善专业 Skill 与报告发布方式（F8、F9）

专业职责单独整理为测试计划、独立计划评审、结果复核和报告 Skill；QA 返工材料组织也优先在 Skill/交接约定中解决。报告正文、Dashboard、证据由 Agent 按 Skill 生成。发布建议复用当前固定工程节点，由它校验并上传、确认远端回执；与模型自主发布作取舍后再决定，不为此先增加平台通用发布系统。

退出条件：Skill 在真实项目计划中抓出核心漏项，同时不将完整脚本实现错压给规划；独立评审与结果复核职责清楚。报告对外可查看且不混淆生成/发布/产品通过，失败和未知发布结果可恢复。两个 Pipeline 仍独立，由人带报告启动修复 Issue。

### P3：配置体验、标准升级和第二项目验证（F5、F6、F9）

围绕已定 Gate/参数/环境交接设计精简画板和任务结果页，保持配置保存、运行生效与标准升级一致。用一个小型绿地仓库和一个带既有 CI/文档的棕地仓库验证项目配置和 GitHub 准备流程。部署保持独立，生产/预发等环境规划单列。F3/F4 的版本追溯先评估 Git/归档/工程工具是否足够，不预先实施全阶段快照或平台版本治理。

退出条件：两仓仅改声明的项目配置即可走所选入口，不依赖协调者临时补环境；页面能看 Gate、任务选项和报告，升级保留本地选择和旧 Run。演练缺输入、返工及外部结果未知；正常人工决定下一任务不记作救援失败。未覆盖的部署/供应商范围明确保留。

### P4：验证投入是否真的带来工程收益

对照三种方式：A 单 Agent + 项目规则/Skills；B 当前模板流程；C 做减法后的受控流程。单 Agent 是实验对照，不预设取代多人/多角色流程。各组使用同一需求、基线、模型条件、权限、预算和独立验收规则；预先界定必要人审，不能给 A 不同授权后比较耗时。

先选三个匹配任务：绿地小功能、棕地明确缺陷、测试发现问题后修复复测。小样本用于发现差异，不做统计显著或普适提效承诺；有明显差异再扩样。避免后一组直接复用前组解法，记录模型容量/外部网络等干扰。

| 维度 | 记录什么 | 不接受的替代指标 |
|---|---|---|
| 功能满足度 | 独立 AC 通过、漏项、真实用户旅程、未验范围 | PR 数、代码量、测试数量 |
| 工程质量 | 缺陷严重性、遗漏、回归、版本一致性、恢复及证据完整性 | Agent 自报完成、全流程绿灯 |
| 效率 | 从输入到可验收的总时长、人的实际分钟、首次与再次接入成本 | 只算 Agent 编码时间 |
| 自动化效果 | 预期人工检查与非预期救援分别计数、无人工修状态完成比例 | 把取消审批视为提效 |
| 运行成本 | 模型调用/成本、重复测试、环境准备和日志维护 | 只看 token 或执行步数 |
| 可复用性 | 第二仓配置差异、必须改模板/代码的次数、升级成本 | 一个测试仓多次跑通 |

增加一层或节点，必须能说明它减少了哪种缺陷或人工工作；如果没有收益，就删除、合并或退回可选配置。必要人工检查保持明确，不把“零人参与”当唯一目标。

## 8. 暂不建设与迁移约束

- 暂不建设通用表达式/变量语言、事件总线、角色本体、独立交接服务、全局制品注册中心、跨项目智能调度器。
- 暂不以增加并行 Agent、流程嵌套、组织权限或远程运行集群证明“平台化”；有真实任务和隔离证据再进入。
- 不把所有项目检查固定成平台语义，也不把所有校验交给提示词。
- 不把不可变交接、候选绑定、人审三个问题合成一个大而全“治理框架”；优先各自最小可复验改动。
- 新配置能力用于未来任务；旧 Run 保持冻结定义和历史文件事实，不能补造当时不存在的快照。旧任务确需新能力时用正式受支持入口，明确哪些保证只从升级后成立。
- 源码、模板、安装、升级、文档及第二仓应用必须一起列入交付；只改测试仓或当前运行副本不算完成。
