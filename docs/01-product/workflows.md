# 智能体编排产品需求

状态：需求基线 v1，2026-10-05。按用户授权采用推荐方案并自主推进；G1 结论见 [评审记录](workflows-review.md)。本文件是新阶段契约，扩展原实验版单 Agent 范围。

## 背景与目标

GitHub CI 与平台会话已形成研发流程的接入方式。阶段跳转依赖外部调度、多个 CI run 和交接回执；用户需要在多个系统查找当前阶段、反馈和恢复入口。新的平台能力让操作者在一个工作流运行中配置、观察和调整节点，处理失败、人工反馈与循环。

目标用户是配置流程的平台管理员，以及发起任务、与 Agent 交流并处理必要确认的工作流使用者。首版为受信任用户提供同机、自托管服务，管理员承担原生执行器、凭据、工作目录和运行成本的维护责任。

成功标准：用户从网页创建或导入流程，拖拽配置节点及连接，绑定真实 Agent 和 Connector，在独立测试仓库完成真实任务；流程经历人工确认、回退、继续和外部回写后仍属于同一运行，记录可追溯。

## 责任与业务闭环

| 能力 | 责任主体 | 可观察结果 |
|---|---|---|
| 定义和变更流程 | 平台管理员 | 有版本的节点图，配置校验结果，可供发起任务 |
| 发起和控制运行 | 授权用户 | 一次任务对应一个运行，可查看、停止、继续及指定回退 |
| 工作与澄清 | 节点所选 Agent | 持续会话、真实输出与产物、明确交接结果 |
| 外部动作 | 已配置 Connector | 外部资源或动作回执，以及明确失败原因 |
| 必要确认 | 运行所有者或管理员 | 批准、拒绝或要求返回某节点，附理由并留痕 |
| 异常恢复 | 平台和操作者 | 已完成记录保留；不确定的外部效果不被悄悄重放 |

主旅程：配置资产 → 编排和校验 → 输入任务并启动 → 节点执行或等待 → 按结果分支／循环 → 输出交付结果。GitHub 管理 Issue、分支和 PR；原生执行器管理模型、Skill 和工具执行；平台管理跨节点进度和运行控制。

研发场景以可导入模板提供，模板可以有需求、设计、开发、QA 等节点；平台核心接受任意节点名称和合法连接。

## 对象首次可用与生命周期

| 对象 | 创建、核验和使用 | 变更与退出 |
|---|---|---|
| Workflow | 管理员网页创建或导入，配置节点／连接，校验后保存 | 保存新版本；运行冻结原版本；停用后不能新建运行，历史保留 |
| Agent | 复用 Agent 管理入口配置、授权、检查与试运行 | 原有配置快照和禁用规则继续适用 |
| Connector | 管理员配置受支持操作、目标和凭据引用，并测试连接 | 更新影响新运行；停用阻止新动作；记录保留，不导出密钥 |
| Run | 授权用户选流程、填写输入并指定本机任务工作区后启动 | 持久记录节点执行，等待、停止、恢复、结束；历史只读可查 |

同一节点可因循环多次执行，所有执行记录保留。同一个运行中，首版一次只执行一个节点。多个 Agent 可按节点接力工作，工作区在运行内共享；不同运行不得并发修改同一工作区。

## 当前范围与规则

P0：可视化编辑、节点拖动和连线；保存／导入／导出；Agent、Connector、人工确认和结束节点；按具名结果选出边；向前推进与回退循环；运行图和历史；会话跳转；停止和显式恢复；真实 GitHub 接入示例。

默认从配置的入口节点开始。管理员可配置可直接进入的节点；启动选择这些入口时必须补齐该节点声明的输入。入口改变不能伪造前序节点成功或跳过权限检查。

Agent 会话一轮结束不等于节点完成。只有正式交接结果才能推进；澄清留在原节点。人工自然语言反馈交给当前 Agent 理解，Agent 建议回退时用户可确认；用户也可通过运行控制直接选择允许的目标节点。

流程可选择自动推荐或人工确认策略。自动推荐允许 Agent 根据任务选择合理默认并记录判断；定义为必须确认的破坏性动作、权限扩大等仍需人工授权。工作流选项不得提高 Agent 原有工具／沙箱权限。用户已有明确授权不重复征求。

停止应阻止新增节点和动作，并请求终止当前本机执行；已在外部完成的效果不会因停止被撤销。重试与继续必须说明会重复什么、保留什么。旧节点迟到的交接不能覆盖新节点进度。

P1 后置：并行 fan-out/join、远程 Worker、集群调度、复杂组织权限、定时触发管理、通用脚本表达式语言和可插拔第三方节点市场。本阶段通过接口／网页发起运行，GitHub 作为首个外部 Connector；不承诺全部 CI 特性平移。

## 用户故事与验收

| ID | 用户动作与结果 | 验收证据 |
|---|---|---|
| WF-01 | 管理员从空白或模板创建图，拖动、连线、修改参数、保存并重新打开 | 浏览器真实操作，节点位置及连接保持；非法连接明确拒绝 |
| WF-02 | 使用者选择流程并启动；重复提交同一请求不产生第二个运行 | API 和网页记录，配置快照与请求去重核验 |
| WF-03 | Agent 节点真实执行；用户在同一会话澄清；交接后才进入下一节点 | 原生输出、工具事件、会话与节点执行关联 |
| WF-04 | 在同一运行内执行成功分支与失败回退，修复后重新交接 | 独立测试仓库真实修改、失败与成功测试日志，完整节点历史 |
| WF-05 | 用户批准／拒绝，或自然语言提出回退建议并确认目标 | 网页操作记录，节点及审批身份可查 |
| WF-06 | Connector 创建／更新真实 GitHub 资源，回执能定位外部结果 | 独立仓库的 Issue／PR 链接，无重复外部对象 |
| WF-07 | 运行中停止后不继续推进，显式恢复仍保留工作区和已完成记录 | 活跃执行停止实测，恢复结果及重复回执拒绝 |
| WF-08 | 平台重启后等待和历史恢复；不确定动作明确待核验 | 重启实测，无自动重复副作用，无永久假运行 |
| WF-09 | 未授权用户不能查看、启动、审批或操作他人运行；禁用资产不能新使用 | 真实 HTTP 身份交叉测试，界面错误反馈 |
| WF-10 | 修改图只影响新运行；旧运行始终显示自身版本 | 双版本运行对照，不改在途定义 |
| WF-11 | 首次安装和已有数据库升级可用；原 Agent 会话功能保持 | 公共安装／启动命令、迁移及既有全套回归 |
| WF-12 | 用户可看见当前节点、等待原因、失败详情、下一步入口与产物 | 浏览器运行详情检查，不依赖终端或直改数据库 |
| WF-13 | 用户提出边界明确的 bug、脚本或配置修复，系统采用与工作匹配的短路径，不强制补写 PRD／设计 | 同一任务保留必要准备、真实修复与验证；未执行的阶段没有伪造的成功记录 |
| WF-14 | 用户未指定起点时，Agent 根据已有依据判断阶段适用性，从允许的交接目标中选择；用户明确指定起点时按授权入口执行 | 真实路线与判断依据可查；既覆盖跳过，也覆盖不能跳过的反例 |
| WF-15 | 交接后用户补充或纠正要求，能够将反馈带回合适节点继续处理 | 先停止或隔离旧执行，再通过正式回退／接续入口传递新要求；旧回执不能推进新执行，不丢失已有产物 |

## 研发模板的典型旅程与具体 AC

这些场景是研发模板的产品契约；内核只提供通用入口、合法连线、交接、等待、运行控制和通知能力，不内置“修 bug”等业务分类。用户可以只说一句话，无需显式要求 Agent 先澄清或跳过某阶段。

| 场景 | 应有行为 | 对应故事 |
|---|---|---|
| 新功能的一句话需求 | Agent 判断信息是否足够，普通选项按推荐推进，关键歧义才澄清 | WF-03、14 |
| 边界明确的 bug 修复 | 直接走修复所需路径，可不运行需求、设计节点；复现、修复与回归保留 | WF-13、14 |
| 已知部署脚本／配置问题 | 在具备原因与预期行为时进入修复，不为形式生成产品 PRD；执行相关脚本与失败恢复验证 | WF-13、14 |
| 仅缺设计、实现尚未开始 | 复用已有需求基线，从允许的设计入口开始；不重新做需求确认 | WF-02、14 |
| QA 验收失败 | 按原因返回开发、设计或需求；保留失败证据，修复后重新验证 | WF-04 |
| 人工拒绝／自然语言要求回退 | 将理由和目标传入下一次执行；目标有歧义时澄清，明确授权不重复确认 | WF-05 |
| 已交接后补充要求或改回退目标 | 停止或隔离原执行，保留产物和记录，按最新要求重新接续；不可并发修改同一工作区 | WF-07、15 |
| 自动推荐与必要人工确认 | 一般决策自主推进；明确固定门禁或权限扩大仍等待授权，恢复后接着执行 | WF-03、05、09 |
| 停止、重启、重复输入和外部响应未知 | 不丢历史、不重复启动或重复外部写入；明确恢复入口 | WF-02、07、08、10 |

**AC-13.1：跳过必须是实际执行路径。** 对已提供复现、预期行为和有限修复范围的 bug，允许跳过需求、设计节点，不创建无关 PRD／设计文档。运行记录显示实际进入的节点及跳过依据，不把未执行阶段标为验收通过。仅让两个 Agent 各回复一句“不适用”后再进入开发，不算此项“直接跳过”通过。

**AC-13.2：缩短路径不等于取消验证。** 保留工作区／分支等必要准备、任务关联、修复、针对改动的回归，以及模板要求的独立校验和交付。纯工程改动不强制跑无关产品端到端用例，但必须说明选择验证范围的依据，不能跳过真实受影响能力和失败恢复检查。

**AC-14.1：两种进入方式。** 管理员配置允许入口和自主交接目标。用户可明确指定从开发或设计开始；也可只提任务，由 Agent 根据 SOP 和已有信息选择合法的短路径。图必须提供相应路径，提示词不能越过图权限。必要准备与关联信息可由前置步骤完成，不能因选择起点而丢失。

**AC-14.2：不能跳过的反例。** “修一下推荐，不太对”这类无法判断预期行为的任务不得直接猜实现；缺少关键业务规则时先澄清，需要改变结构时进入设计。任务标题包含 bug、脚本等词语，不构成自动跳阶段条件。

**AC-15.1：纠正交接。** 用户明确指出“应回需求而非设计”后，保留此次纠正及原交接记录，停止或隔离原目标执行，再从允许目标接续。旧工具调用、迟到结果和重复提交不得覆盖新执行。必须经正式运行控制入口验证，不能直接修改持久表恢复。

上述条目是验收要求，不代表全部已实现或实测；逐项现状以 [验证记录](../03-delivery/workflows-verification.md) 为准。

## 质量、依赖与假设

首版针对同机低并发；节点数和循环次数设明确上限，超过时报告原因并停止推进，防止无限执行。网页刷新、网络重试和进程重启不得悄悄新建任务或重复外部写入。不宣称跨系统 exactly-once；结果未知时要求核验。

依赖可用的 Codex 登录、已授权的 GitHub 凭据、独立任务目录和持久磁盘。默认采用受信管理员管理 Connector；本阶段不托管匿名、不可信代码。技术实现承担权限、版本快照、幂等和恢复契约。

验证由实施者通过独立测试仓库与隔离平台实例执行，保留可追溯证据；用户检查页面和体验。当前假设：串行节点接力足以覆盖第一版；后续出现真实并行需求再扩展。原测试仓库的部署脚本问题属于独立任务，不构成本平台研发范围。

## 2026-10-05 用户对齐：通用智能体编排

用户授权在开发分支自主实施、验证和调试，名称采用“智能体编排”。研发是主打模板而非内核业务。Agent 自主意图判断及分支交接使用虚线；确定规则流转使用实线，不引入独立意图模型。普通确认仍可由 SOP 与自然语言对话完成，回复结束不等于节点完成。固定 Gate 可配置，但不强加到每个研发阶段。

Hook 是时机，动作是能力，参数映射由模板配置。节点启动、最终回复完成、交接完成等事实产生结构化事件；通知可引用 Agent 原文、交接参数及平台链接，内核不得解释回复来判断业务结论。外部通知失败独立呈现和恢复，不重跑 Agent 或交接。GitHub/GitLab 语义只由集成动作与模板承担。

新增验收：虚实线有真实执行语义并可配置；同一节点的多个自主分支可读可编辑；节点显式完成沿固定线推进而普通回复不会推进；正常交接、用户澄清接续、QA 返工和 Issue 回写均可通过模板覆盖；旧定义与旧运行兼容，图版本不被迁移覆盖。
