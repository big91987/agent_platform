# 治理工具真实复验：有定位能力，模型输出仍不稳定

本次检验工具能否检查代码组织与架构规范、给出针对具体对象的建议，并正确拒绝不完整或不可靠的模型结果。Model Relay 仅为固定源码样本，未改业务代码、未执行产品验收。

**结论：工具核心范围是代码和架构治理。新增报告能列出具体文件、函数/类型和原文，模型建议也已收紧到职责与依赖调整。但三轮中只有第一轮通过完整协议和引用校验，第二、三轮被拒收，尚不能称为稳定可用的模型评审链路。**

三轮均使用同一产品源码摘要、61 份源码和上下文、11 个检查项。材料基于产品提交 `d03fe5b6843ea6a274a43411a92dad237b902313`。开发过程中明确了中文及返回字段要求，所以各轮评审策略不同，不能以发现数量比较模型质量或计算稳定性统计。每轮完整策略在 review-policy.json，实际模型、用量、耗时及产物摘要在 run.json。

## 判断工具时应分开的事情

- **架构范围**：这次返回围绕职责、分层、状态、依赖和规范对齐，没有把产品业务验收当成工具目标。引用既有业务回归只用于保护原行为，不表示已执行。
- **报告对象**：第一轮报告由解析事实对应到了原文所在函数和类型，能够显示具体对象；“调整建议”仍是模型意见，不能视为已确认的目标设计。
- **拒收是否正确**：第二轮多字段、第三轮歧义引用都应拒绝。未完成回执保留已有规则结果与原始模型返回。
- **模型判断是否可靠**：真实引用不证明概括正确，第一轮对锁的概括即为反例；不能靠手工润色或一次成功宣称语义可靠。
- **使用成本**：全量材料每轮约 22.6 万输入 token，耗时约 80–145 秒，当前更适合基线体检；本次未实现增量评审，也不凭用量估算实际账单。

后续改进对象应是模型输出、引用定位的稳定性与评审范围成本；不通过放宽校验、修改产品规则或协调者代写发现来掩盖这些问题。本次没有自动重试、自动回退或增加新的兼容协议。
