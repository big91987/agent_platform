# Model Relay 架构检查：发现了什么，这次改了什么

**本次发现的主要问题是：后端多种职责集中在一个包里，业务规则与 HTTP、数据库处理混在一起，前端也缺少功能边界。本次交付改进了检查工具并将它接入 Model Relay，尚未重构产品代码。**

以下是 DeepSeek 对固定版本源码的架构评审结果，共 7 项待复核发现。它们用于确定后续整理代码的重点，不代表已经证实产品功能出错，也不代表已经完成修复。严重程度是模型对架构风险的判断，不是生产故障等级。

## Model Relay 的主要问题

| 检查发现 | 在代码中具体是什么意思 | 对后续开发的影响 | 模型评估 |
| --- | --- | --- | --- |
| 后端职责集中在一个包 | 网关、控制台、计费、存储迁移和备份都在 `internal/relay` 中，包内可以直接互相访问 | 难以约束模块依赖；一处改动需要考虑较大范围的影响 | 中 |
| 请求处理、业务操作和数据库写入混在一起 | 控制台 HTTP 处理函数直接执行校验、业务判断、SQL 和事务 | 业务操作难以独立测试、复用；整理时必须保留原有事务的一致性 | 高 |
| 同一业务规则有多份实现 | 模型授权和费用汇总的部分规则分别在多个路径中实现 | 后续调整可能漏改某处，造成不同入口的口径不一致 | 中 |
| 选路策略与外部调用细节耦合 | 路由选择直接依赖 HTTP 请求和数据库；上游协议、鉴权和网络配置散布在多处 | 策略难以独立测试，新增上游或修改选路需要理解多处代码 | 中 |
| 当前架构规则不能检查包内分工 | 规则把 `relay` 整体视为一个模块，没有表达目标模板要求的内部职责边界 | 即使包内继续混入不同职责，依赖检查也可能一直通过 | 中 |
| 管理功能与请求派发共享状态和锁 | 控制台操作与选路共用 `Server` 中的锁和运行状态 | 存在相互影响的风险；是否构成实际性能瓶颈还需测量 | 低 |
| 前端功能集中在一个脚本 | 多个页面的渲染逻辑和交互状态集中管理 | 页面增加后，更难定位改动和隔离回归影响 | 低 |

这 7 项来自工具调用模型后生成的标准报告，上表将其解释为便于阅读的表述。原始发现、代码引用和建议保留在[最终标准报告](round-06/report.json)及[模型原始返回](round-06/model-result.json)中。模型建议仍需复核，不能直接作为已确认缺陷或重构方案。

## 为什么规则通过，报告却仍有问题

- **规则扫描：0 条违规。** 只说明代码没有违反当前已声明的包依赖规则。当前规则的粒度较粗，无法判断一个包内是否混入过多职责。
- **模型评审：11 个检查主题都有结果，其中 7 项存在偏差、4 项符合要求。** “检查完整”表示这些主题都得到回答，不表示全部合格；这些判断归纳为上表的 7 项发现。
- **引用校验通过。** 说明模型引用的原文能在同版材料中准确定位，不等于其风险判断和修改建议已经得到验证。

因此，本次结论是：**Model Relay 在现有依赖规则下通过检查，但与目标架构模板仍有差距；工具已经提出可供复核的具体整理方向，产品重构尚未实施。**
