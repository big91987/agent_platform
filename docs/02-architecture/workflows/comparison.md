# 流程方案比较与选型

[流程方案目录](README.md)

本页只维护跨方案比较，不重复方案的执行细节。当前已记录 [Runner 直接调用 Agent](runner-direct.md) 和 [GitHub CI + Agent Platform](github-agent-platform.md)；它们不是互斥或穷尽的路线，新增方案后按相同维度补充比较。

## 选型维度

| 维度 | Runner 直接调用 Agent | GitHub CI + Agent Platform |
| --- | --- | --- |
| 部署复杂度 | 组件少，依赖 CI、本地运行器与持久目录 | 增加平台服务、数据库、账号和接口运维 |
| 多轮人机交互 | Issue 评论触发下一次执行；对话体验受 CI 调度影响 | 网页即时对话、流式事件、队列与工具审批，CI 不必承接每句话 |
| 会话管理 | Full 版已支持原生 Session，但由每套 Harness 自己实现 | 通用平台统一管理，会话独立于 CI run |
| 状态恢复 | Runner 文件检查点与脚本负责；与固定持久机器耦合 | 执行状态在平台，业务状态仍在外部登记；跨系统仍需协调 |
| 流程变更 | 改 YAML、控制器、入口和提示规则 | 当前仍要改外部模板与集成；尚未成为可视化编排 |
| 返工与人工介入 | 能实现，但需控制器维护循环和暂停恢复 | 工具交接及自然语言接续更直接，撤回仍涉及 run 和会话两端 |
| 可观测性 | Actions、Issue 和 Artifact 是主要入口 | 增加持续会话与工具视图，但总流程状态仍分散 |
| Agent 复用 | 更多能力跟随具体 Runner 集成 | 可将同一个 Agent 能力用于网页、SDK 和不同外部系统 |
| 故障面 | 主要是 CI、CLI、脚本和本地状态 | 还需处理 API、工具绑定快照、CI 超时与跨系统回执一致性 |
| 适用情形 | 较固定、交互少、以仓库批处理为中心的任务 | 多轮澄清、人工介入多、需要通用 Agent 服务的任务 |

没有“CI 做不到回退”的绝对限制：脚本内循环或跨 run dispatch 都能实现。真正的代价是，为表达长期运行的业务流程，需要自己补齐状态、恢复、可见性和跨系统一致性。

## 如何选择

- 任务较固定、以仓库批处理为中心、用户介入较少：优先评估 Runner 直调方案，以较少组件完成任务。
- 需要多轮对话、实时可见的工具执行、多个接入渠道和可复用 Agent：评估 GitHub CI + 平台方案，同时承担跨系统状态协调成本。
- 若主要痛点变成跨 run 回退、长时间等待、取消恢复和整体状态不可见，应进一步评估统一流程编排，而不能只靠不断添加 CI 条件解决。

“将编排放在平台内”是已讨论的候选方向，尚不是已实现方案，也不是预先排除其他方法后的唯一结论。若推进，应建立独立方案文档，说明流程状态由谁拥有、如何执行节点、如何接入 CI、如何迁移在途任务以及验证证据，再纳入本页比较。

## 评价约束

- 比较的是执行和控制责任，不仅是是否使用某个产品或是否具有图形画布。
- CI 可以通过脚本内循环或跨 run dispatch 支持返工；应比较维护成本和控制体验，而不是断言 CI 不能循环。
- 平台化不会自动消除工具缺失、权限问题、重复副作用和迁移风险；这些应作为各方案的工程边界评估。
- 已实现、建议、真实验证和未测范围分别记录；某条链路通过不能泛化成全部故障恢复通过。
