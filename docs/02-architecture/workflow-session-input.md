# 工作流角色指令与会话输入

状态：已接受设计，本轮生命周期补齐已实施并验收。依据用户确认的角色、项目规则、工具及会话输入四类责任。

## 输入与执行

Agent.instructions 仅保存角色职责；Codex 映射为 developerInstructions，并原生发现工作目录内 AGENTS.md。平台不得修改该文件或再手工复制。工具通过已有注册层传递，任务、节点 prompt、交接、修正走首轮 User Input。

Workflow.context_version=1 选择 Markdown 输入协议；缺失/0 保留旧冻结定义协议。节点沿用 prompt 字段（Session Prompt），新建自主交接节点必须恰有一个 {{handoff}}，未知或重复占位符拒绝。固定节点可省略占位符；存在时展开为空。混合出边原样保留并显示兼容提示，不静默丢失。固定完成说明独立生成。

共用 workflowSessionPrompt 生成节点工作说明及合法目标/策略；workflowAgentInput 追加原任务、用户修正、最近的上游交接、最近的每个 Connector 回执引用及当前回退原因。正文 Markdown，不复制全图或累计 Agent 结果。Connector 回执保留执行身份与材料定位，长输出通过日志工具读取。已成功投递的用户修正按来源/消息标识保留，不按关键词判断有效性，不把运行数据回写配置。

预览 API 使用当前草稿并复用运行生成器；实际冻结输入在 Run 节点详情查看。Agent 编辑入口明确影响共享 Agent。连线与目标/策略列表使用现有 edges 一份数据；route 只保留旧接口及 Connector 成功失败兼容，新自主界面以目标/策略为主。

## 完成与等待

显式 complete_node/handoff 才能完成节点；固定模式不注册 handoff。新协议增加 wait_for_input(reason, kind) 工具，kind=clarification 或 blocked；它不完成节点，只声明为什么必须等待。自然语言回复不作为完成或澄清信号。

新节点配置 continuation_limit（0–10 次；0 关闭）与 execution_timeout_seconds（0–86400 秒；0 不启用时间限制）。正式模板默认 3 次、14400 秒。正常 turn 结束、未交接且没有明确等待时，由平台在原会话追加一次继续指令；计数与对应完成消息持久化，事务检查当前 Run/seq/会话，重启和重复 tick 不重复排队。达到上限时留下明确等待原因，不宣称完成。失败、用户停止、权限撤销不自动续跑。等待后新用户输入沿用同一会话；轮数预算属于节点执行，不被每条消息重置。

这是执行器无关的平台生命周期检查，不把所有原生 Stop hook 或供应商都称为已支持。已有受信原生 hook 仍可执行，不继承任意基础 Agent 的本机命令。

## 安装与兼容

唯一维护源的正式模板/安装器设置新协议、角色与 Session Prompt 分离及有界持续推进。升级原 manifest 保留对象身份；旧 Run 的冻结定义、快照、原生会话不改，显式旧路径继续。新增节点使用新配置。开发实例升级前备份、核对无在途执行进程，重启后对旧 Run 逐项核对。不自动合并源 main。

## 验收

AC-01 角色无任务/Run/前序结果，实际消息包含任务。
AC-02 默认/外部工作区 AGENTS.md 原样且原生发现，角色同时生效。
AC-03 需求/设计/开发三个节点 Markdown 且无累计历史 JSON。
AC-04 目标/策略/画布一致，占位符与目标校验，预览与执行生成器一致。
AC-05 固定无 handoff；自主只接受合法目标；重复完成仅推进一次。
AC-06 澄清沿原会话追加；修正跨节点可见。
AC-07 交接/QA 回退/人工回退携带问题、版本和可访问产物。
AC-08 停止/恢复/重试/迟到结果隔离，无重复副作用。
AC-09 提前收尾有界续跑；真实等待/用户停止独立处理。
AC-10 Run 查看实际角色、项目规则来源、工具与输入，敏感配置不暴露。
AC-11 新安装/manifest 升级一致，旧冻结 Run 保持兼容。
AC-12 真实 Codex 路径；其他执行器据实际结果标记未测。

## 节点生命周期补充契约

一轮结束是执行事件，不等于节点完成。沿用现有 running/waiting/completed/failed/stopped 状态及调度状态：正常交付以已接受的 handoff/complete_node 为准；需要用户输入以已接受的等待工具为准；用户停止与执行失败分别按平台事实处理；没有交付或等待信号的正常收尾才有界接续。局部工具报错如已由 Agent 恢复，不直接等同整个执行失败。

节点 `allow_user_input` 为布尔开关，公开业务概念为“允许请求用户输入”，沿用一个 `wait_for_input(kind, reason)` 工具，不再新增同义的 need_user_input。新建节点与标准安装明确设置 true；已有 context_version1 定义缺失字段兼容原先开放行为，false 才显式关闭；context_version0 继续旧协议。开关按 Run 定义冻结。关闭时工具列表和服务端事务同时拒绝；生成的 SOP/继续消息不能要求使用未开放工具。需要澄清应交给已配置的合法目标，无信息且无出口时明确报告阻塞、保留现场，达到配置上限暂停，不编造答案、不创建新 Run 绕过限制。开关限制 Agent 主动请求，用户仍可主动补充或停止。

澄清需附可作答的具体问题/决定事项；blocked 说明真实外部条件，不能与用户问题混淆。等待记录绑定当前执行和运行中的输入消息。接受新用户输入原子清理等待；有排队/投递中的新输入时不接受旧等待。同一原生轮中已接受 steering 修正后，旧等待也不能盖回；该轮正常结束后沿原会话继续处理。跨节点只传已成功投递的 completed/steered 用户补充；明确丢弃、停止或投递结果不确定的输入保留审计，不被提升为新需求。

新协议每次调度 Claim 在同一事务轮换现有节点工具凭据，原进程的迟到请求不能提交到下一轮；不增加第二套执行身份。角色/项目规则/工具配置语义不变，仅执行凭据更新。当前 seq、停止状态、已保存结果及待处理用户消息继续由原事务检查。重复已接受结果只复用原结果，交接后等待 Agent 安静才推进。重启中断中的执行标记失败并提示检查副作用，不自动重放。

平台 Stop 检查不另调用模型判断意图，也不扫描问号或关键词。受信原生 Stop hook 在执行器进程内运行；平台只在整个 Executor 返回且 scheduler 已安静后检查。原生 hook 的内部接续不另入平台队列；完成信号优先，平台不能对同一次结束再排队。真实 Hook 协同记录见验证表。具体 Codex 行为参考[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)，平台契约仍不依赖该执行器专有 Hook。

上限是暂停原因，不是完成或虚构的用户问题。页面根据 clarification/blocked/limit/disabled 分别显示原因与下一步。完成/交接仅证明生命周期出口被接受，交付质量继续由固定测试与独立 QA 负责。
